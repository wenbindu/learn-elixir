# BEAM Path 文案与讲解准则

这份准则供站点维护者使用。读者主要是第一次接触编程的中小学生。文案应帮助他们
理解任务、运行代码，并准确复述实验结果。

## 我们在和谁说话

- 读者可能只写过几行代码，也可能从没打开过终端。
- 不假定读者已经理解终端、进程、协议等术语。
- 先给出可以执行的小任务，再补充原理。
- 把报错写成可以观察和处理的结果。

## 每段话怎么写

1. 先说眼前要做什么，再介绍术语。
2. 一个句子尽量只放一个新概念。
3. 英文术语首次出现时，紧跟一句普通中文解释。
4. 少用“掌握”“构建体系”“完成验收”等课程或工作用语。
5. 分开说明“这次看到了什么”和“还不能推出什么”。
6. 按钮写具体动作，例如“运行代码”，不要只写“进入”。
7. 使用短句。删掉不影响含义的形容词、口号和重复总结。

## 中英文不是互译副本

两种语言版本应共享同一份教学骨架，但分别写成自然的中文和英文。

以下内容必须一致：

- 学习目标、概念范围和先修要求。
- 示例的输入、输出、失败条件和过关标准。
- 同一案例的身份、阶段、公开接口和产物。
- 技术保证与限制。例如，中文不能写“至少一次”，英文却只承诺有限重试。

以下内容可以本地化：

- 人名、地点、样例文字和生活场景。
- 标题、解释顺序和帮助记忆的比喻。
- 为理解文化背景而增加的一句上下文。

完成一版后，不要逐句搬到另一版。把译文单独读一遍：若离开原文就显得生硬、含义不明，
应按目标语言重写。切换语言后，学习者不应突然换项目、换接口或换验收题。

## 中文写作规范

- 使用自然、当代、简洁的中文。短句可以有节奏，但不要故意仿古，也不要堆砌成语。
- 先用日常话说清问题，再给正式术语。例如先写“队伍已经满了，新任务不能悄悄排下去”，
  再介绍“有界队列”和“背压”。
- 中国历史与文学可以帮助记忆，但应服务于技术关系。书院、驿站、校刊、快递和食堂排队都
  可以使用，不必每一课都落到战争、粮草或朝代制度。
- 不假定读者熟悉某部名著或历史制度。需要背景时，用一句话交代，不用典故考学生。
- 少用“赋能”“闭环”“抓手”“体系化掌握”等工作汇报语言。也不要把普通练习写成宏大口号。
- 代码里的正式名称保持不变。中文只负责解释，不把 `callback`、`mailbox` 或 `runbook`
  改成无法检索的自造名称。

## 英文写作规范

- 使用清楚、自然的国际英语。优先写明确的主语、动作和结果，不照搬中文语序。
- 标题应能独立说明问题。中文“粮车有限”若不保留历史背景，可写成
  “A queue has finite capacity”，不要直译成 “There are only so many wagons”。
- 避免把“公文”“营寨”“断句”等词逐字翻译后留下没有上下文的隐喻。可以改用 school
  mailroom、parcel tracking、cafeteria line 等日常场景。
- 若保留中国故事，应写出名称并补一句背景。例如先说明 Tang relay stations carried official
  messages，再说明它与 request/reply 的对应关系。不要使用失去出处的半截比喻。
- 不把“欧美读者”当成一种文化。避免只有某个国家、宗教、运动或学校制度中的读者才能懂的
  俚语。人名与样例应保持多样，但不能改变技术契约。
- 不为了显得亲切而滥用感叹号、俚语或儿童腔。面向中小学生，仍应准确、平静、尊重读者。
- 英文术语、API、异常名和返回值保持官方拼写；不要为了和中文标题押韵而改写技术名称。

## 历史与文学比喻怎么用

比喻只用于引出概念，不能代替技术定义。每个故事桥包含三项：

- 场景：使用常见历史、文学或生活场景。
- 对应：说明场景中各角色对应哪些代码角色。
- 边界：指出比喻与真实机制不同之处。

不要强行加入文化元素，也不要把文学情节写成历史事实。古代制度只使用常识性场景，
避免依赖有争议的细节。

日常比喻与历史比喻遵守同一条规则：只能帮助理解一个关系，不能承担完整定义。优先使用读者
亲手见过的场景解释必学概念；历史和文学场景更适合帮助记忆。不要连续用多个角色对应一个
术语，也不要让学习者先研究故事才能开始写代码。

本地化比喻时有两种安全做法：

1. 保留原文化场景，并给目标语言读者补一行背景。
2. 换成目标语言中自然的日常场景，但保留相同的技术对应与边界。

不要只替换几个名词。若中文讲驿站，英文不能只把“驿站”换成 station，却保留一套英语读者
无法理解的官职和制度。

## 术语的两层写法

先给一句可复述的说明，再补充准确限制：

> mailbox 像每个进程门口自己的收信篮。准确地说，它是这个进程收到、但还没处理的
> 消息队列。

代码、命令、返回值和 API 名称保持原样。不要用自造昵称替换正式术语。

术语首次出现时必须完成三件事：

1. 给出正式名称，方便以后搜索文档。
2. 用一句日常话说明它在当前例子中做什么。
3. 补一句准确边界，说明它不保证什么或容易与什么混淆。

中文可写成 `mailbox（进程收到但还没处理的消息队列）`。英文可写成
`mailbox - the messages this process has received but not handled yet`。后续使用正式名称即可，
不必每次重复解释。

`term`、`callback`、`fixture`、`profile`、`runbook`、`idempotency` 和 `backpressure`
等词不能只靠上下文猜。缩写首次出现时也要说明职责。中英文应使用同一个概念标识，解释可以
分别本地化。

## 运行前思考题怎么写

每个关键示例在运行前给学习者一个可以验证的预测，不要先泄露答案。固定使用下面的顺序：

1. **预测**：只问一个可观察结果，例如返回值、mailbox 长度或哪些 PID 会改变。
2. **理由**：请学习者用刚学到的一条规则解释选择；允许写“还不确定”。
3. **观察点**：提前指出运行时只需记录的一到两个信号。
4. **运行**：执行完全相同的输入，不在中途偷偷改条件。
5. **对照**：比较预测与结果；若不同，找出是哪条假设需要修改。

好的问题应短、具体、能由本次实验回答。例如：

> 调用者等到 timeout 后，迟到的 reply 会消失，还是会留在 mailbox？先画出消息时间线，
> 再运行实验。

避免“谈谈你的理解”“你学会了吗”或一次询问三个概念。选择题的错误选项也应来自真实误解，
不能明显荒唐。预测、提示和答案要分开；提示只推进一步。

## 与 Java、Python、JavaScript 对照

对照用于纠正常见心智模型，不用于宣布哪门语言更高级。只在概念转弯处使用，例如匹配与赋值、
模块与 class、tagged result 与异常、BEAM 进程与共享线程、异步与背压。

- 比较语义，不只比较标点。固定观察状态归谁、怎样通信、失败怎样传播、怎样取消、容量在哪里。
- 使用“常见 Java/Python/JavaScript 代码通常……”等有限表述，不写“Java 总是……”或
  “Python 不能并行”。
- Java 已有虚拟线程；Python 有不同运行时和 free-threaded 构建；JavaScript 也有 Worker
  与不同 isolate。若比较依赖具体运行时，必须写出这个前提。
- BEAM 进程通常隔离状态并通过消息合作，但 ETS 等机制允许共享访问；不要把教学模型说成没有
  例外的定律。
- `async`、Promise、Task 或 cast 只说明调用者此处是否等待，不自动说明并发有上限，也不自动
  提供取消、重试或背压。
- 每次对照同时写出代价。例如进程隔离减少共享状态冲突，但消息协议、mailbox 容量和迟到回复
  仍需设计。

一张对照卡最多突出一个差异。不要在初学课中一次罗列三门语言的所有语法。

## 代码示例怎么注释

- 注释只解释意图、数据流、消息去向和失败边界。每个关键步骤用一句短话。
- Elixir 和终端示例使用 `#`，Erlang 示例使用 `%%`。
- 不逐个解释括号、逗号和 `end`。注释不应盖住代码本身。
- 示例加完注释仍要能直接复制运行。

## From Scratch 课程怎么写

- 每门语言分成四段：Scratch 9 课、Foundation 8 课、Intermediate 8 课、Project 6 课。
- Scratch 让读者敢运行；Foundation 让读者独立写模块和基础测试；Intermediate 处理真实输入、错误边界和工具；Project 交付一个小作品。
- Foundation 完成后即可进入 BEAM 主线。不要把语言高级课写成进入并发学习的硬门槛。
- 假定读者不认识变量、参数、返回值、模块和终端提示符。第一次出现时，用一句普通中文解释。
- 一课只解决一个主要问题。连续出现三个新术语时，停下来拆开。
- 先给完整写法，再给缩写。先写 `fn number -> number * 2 end`，再写 `&(&1 * 2)`。
- 遇到 `/1`、`&1`、`|>`、`:`、`;` 等符号，逐段说明它表示什么，也说明它不是什么。
- 函数要分开写“准确名字”和“真正调用”：如 `String.trim/1` 与 `String.trim(text)`。
- 每个例子写清输入、预期结果和一处可修改的位置。让读者先猜，再运行。
- 练习答案默认收起。提示只迈一步，不在第一句给出完整答案。
- Elixir 与 Erlang 分开教学。学完任意一条即可进入 BEAM 主线，另一条可以以后对照。
- 基础课不提前塞入 GenServer、Supervisor、分布式或部署；这些留给主线。

## BEAM 主线怎么写

BEAM 主线不按术语排课。每站只追一个工程问题，例如“超时以后任务真的停了吗”或
“一个 worker 崩了，应该重启谁”。固定顺序如下：

1. 写出一条能够回答的 question。
2. 描述事故现场，并列出能够观察的日志、mailbox、延迟或状态。
3. 展示最小代码，再让读者亲手复现故障。
4. 解释机制和限制，明确这次实验不能证明什么。
5. 给设计模式准确名称，并说明它在本例承担什么职责。
6. 最后才使用故事桥。故事只帮助记忆，不负责提出问题。

同一问题默认只展示一种代码。读者可在 Elixir 与 Erlang 之间切换，选择保存在当前设备。
只有共享协议和互操作课程提供“对照”模式。两份实现必须使用同一组输入、失败条件和
过关标准，不能只做逐行翻译。

## 安装说明怎么写

- 优先使用 Elixir、Erlang 和操作系统的官方页面。不要把搜索结果当作下载入口。
- macOS、Linux、Windows 分开写。提醒读者只执行自己系统对应的一套步骤。
- 版本组合会变化。写清核对官方兼容表，不把旧版本说成永远适用。
- Mix 随 Elixir 提供，不写成第三份独立安装包。
- 遇到管理员密码、学校电脑或家庭共用设备，提醒读者先找家长、老师或管理员。

## 发布前自查

- 第一屏是否说明当前可以做什么？
- 中英文是否保持同一目标、案例、输入输出、失败条件和过关标准？
- 中文是否像自然中文，英文是否离开中文原稿后仍能独立读懂？
- 每个抽象概念附近是否有例子、实验或故事桥？
- 是否连续出现了三个以上没有解释的术语？
- 正式术语首次出现时，是否同时给了日常解释和准确边界？
- 关键代码运行前，是否要求学习者预测一个可观察结果并说明理由？
- 报错是否写成可观察、可处理的结果？
- 比喻是否写清了边界？
- 跨语言对照是否写明运行时前提和例外，而不是绝对判断？
- 一个段落是否只表达一个主要意思？
