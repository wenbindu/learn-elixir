# BEAM Path 文案与讲解准则

这份准则面向站点维护者。目标不是把技术“讲浅”，而是让第一次接触编程的中小学生
愿意读下去、敢于动手，并能在实验后说出真正发生了什么。

## 我们在和谁说话

- 读者可能只写过几行代码，也可能从没打开过终端。
- 读者不需要先证明自己“基础够好”，才有资格开始。
- 读者的注意力来自好奇心、故事和亲手看到的变化，而不是课程压力。
- 出错是一次观察机会，不是能力不足的证据。

## 每段话怎么写

1. 先说眼前要做什么，再介绍术语。
2. 一个句子尽量只放一个新概念。
3. 第一次出现英文术语时，紧跟一句普通中文解释。
4. 多用“我们来试试”“你会看到”“猜一猜”，少用“掌握”“构建体系”“完成验收”。
5. 说明结果时区分“这次看到了什么”和“还不能推出什么”。
6. 按钮写成清楚的动作，例如“运行第一段代码”，而不是“进入模块”。

## 历史与文学比喻怎么用

比喻是一座桥，不是技术定义。每个“故事桥”都要包含三件事：

- 熟悉的场景：驿站、都江堰、戏班、《西游记》等。
- 对应关系：故事中的谁或什么，对应代码里的哪个角色。
- 比喻边界：明确哪里开始不一样，提醒读者回到真实实验。

不要为了“中国元素”强行套故事，也不要把文学情节写成历史事实。涉及《三国演义》等
作品时，应明确它是文学故事；涉及古代制度时，只使用不依赖争议细节的常识性场景。

## 术语的两层写法

先给孩子能复述的一句话，再给准确说法：

> mailbox 像每个进程门口自己的收信篮。准确地说，它是这个进程收到、但还没处理的
> 消息队列。

第一句负责让人敢往下读，第二句负责不把概念讲错。代码、命令、返回值和 API 名称保持
原样，不把正式术语改成自造昵称。

## 发布前自查

- 第一屏是否让读者知道“我现在可以做什么”？
- 每个抽象概念附近是否有例子、实验或故事桥？
- 是否连续出现了三个以上没有解释的术语？
- 是否把出错写成了可安全尝试的动作？
- 比喻是否写清了边界？
- 小学高年级读者能否读完一个段落后，用自己的话复述大意？
