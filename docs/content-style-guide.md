# BEAM Path 文案与讲解准则

这份准则供站点维护者使用。读者主要是第一次接触编程的中小学生。文案应帮助他们
理解任务、运行代码，并准确复述实验结果。

## 我们在和谁说话

- 读者可能只写过几行代码，也可能从没打开过终端。
- 不假定读者已经理解终端、进程、协议等术语。
- 先给出可以执行的小任务，再补充原理。
- 把报错写成可以观察和处理的结果。

## 每段话怎么写

1. 先说眼前要做什么，再介绍术语。
2. 一个句子尽量只放一个新概念。
3. 英文术语首次出现时，紧跟一句普通中文解释。
4. 少用“掌握”“构建体系”“完成验收”等课程或工作用语。
5. 分开说明“这次看到了什么”和“还不能推出什么”。
6. 按钮写具体动作，例如“运行代码”，不要只写“进入”。
7. 使用短句。删掉不影响含义的形容词、口号和重复总结。

## 历史与文学比喻怎么用

比喻只用于引出概念，不能代替技术定义。每个故事桥包含三项：

- 场景：使用常见历史、文学或生活场景。
- 对应：说明场景中各角色对应哪些代码角色。
- 边界：指出比喻与真实机制不同之处。

不要强行加入文化元素，也不要把文学情节写成历史事实。古代制度只使用常识性场景，
避免依赖有争议的细节。

## 术语的两层写法

先给一句可复述的说明，再补充准确限制：

> mailbox 像每个进程门口自己的收信篮。准确地说，它是这个进程收到、但还没处理的
> 消息队列。

代码、命令、返回值和 API 名称保持原样。不要用自造昵称替换正式术语。

## 代码示例怎么注释

- 注释只解释意图、数据流、消息去向和失败边界。每个关键步骤用一句短话。
- Elixir 和终端示例使用 `#`，Erlang 示例使用 `%%`。
- 不逐个解释括号、逗号和 `end`。注释不应盖住代码本身。
- 示例加完注释仍要能直接复制运行。

## 发布前自查

- 第一屏是否说明当前可以做什么？
- 每个抽象概念附近是否有例子、实验或故事桥？
- 是否连续出现了三个以上没有解释的术语？
- 报错是否写成可观察、可处理的结果？
- 比喻是否写清了边界？
- 一个段落是否只表达一个主要意思？
